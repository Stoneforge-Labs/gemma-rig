The 31B is dense — all 60 layers are read for every token, where the MoE reads only its 8 active experts. That is the entire 3x speed difference. It also uses less VRAM than the FP8 26B (19.8 vs 27 GiB) and gives the largest KV cache of the three. Its published advantages are biggest exactly where this rig works: BBEH +9.6, Tau2 (agentic tool use) +8.7, Codeforces +432 ELO.

Vision, audio and files

Vision is on by default in every profile and verified on both the 26B and the 31B — gemma @photo.jpg "what is this?" works on each. GEMMA_IMAGES sets how many images one prompt may carry (default 4).

  • Audio is not available on either model. Both the 26B and the 31B declare audio_config: null — there is no audio encoder in the weights. Only the 12B has one, and using it means giving up this speed and accuracy.
  • Do not set the image limit to 0 on the 31B. vLLM still profiles the encoder and dies on AttributeError: 'NoneType' object has no attribute 'size'. The launcher clamps it to 1 for you. Turning it down saves nothing anyway — measured: KV cache is identical at image 1 and image 4 (115,742 tokens either way).
  • Files are read with the ordinary tools — @file attaches anything, and she can open, edit and write files directly in the working directory.

Yes — context is selectable per boot. GEMMA_CTX overrides the profile default. Bigger context costs KV memory, so if a boot fails on memory, lower it or switch profile.

4-bit costs about 3 points of accuracy and buys speed. Use fast for agent work where she is writing code all night; use quality when the number matters.

Blocking the encoders: tested, and not worth it

The obvious tuning idea — --limit-mm-per-prompt '{"image":0,"audio":0,"video":0}' to reclaim VRAM for text — does not pay off on the 31B, and the two vLLM versions behave in opposite ways:

vLLMvision on (image:4)modalities blocked (image:0)
0.25.1 (rig default)works — 62.8 tok/s, 115,742 KVcrashes
0.26.0crashesworks — 58.5 tok/s, 73,635 KV

Both crashes are the same bug inside vLLM's gemma4_mm.py forward path (AttributeError: 'NoneType' object has no attribute 'size'), just triggered from opposite directions. Blocking the modalities saves about 1.1 GiB of weights but yields a smaller KV cache and slightly slower decode, so there is nothing to win. Vision stays on.

Putting her to work on bugs

She fixes code through a wave: a queue of bounded units, each with a command that proves it is fixed. The driver — not the model — decides when a unit is done.

# 1. write the queue: one line per unit, in the workspace root
#    WAVE.md
- [ ] fix-leak-a: In db.py, close the connection on every path | verify: python3 .../check_fix.py db.py --absent 'conn = connect\(\)'

# 2. run the wave
cd /path/to/Harness
python3 scripts/pi_work_wave.py \
  --workspace /path/to/project \
  --model gemma-4-26b-a4b --no-baseline-gate --final-verify true

A unit only counts when its verify command exits 0 and a commit landed. She gets 20 turns and 12 attempts per unit — enough to self-correct.

Writing a gate that actually works

  • Gate on the defect's own signature, never on a word the file already contains — a gate that is green before any work exists cannot tell a correct model from an idle one. The driver now warns about this at startup.
  • Check the pattern matches the real code first: python3 scripts/check_fix.py <file> --absent '<regex>'. A typo (con = vs c =) silently makes the unit unsatisfiable.
  • Split a big file across units with --max-count 12, stepping the ceiling down (12 → 8 → 4 → 0). 17 fixes in one session fails; four passes succeed.

Tuning — how the profiles were found

Profile the router, then offload the cold experts

The model holds 128 experts per layer and routes each token to 8. On a narrow workload that choice is far from uniform.

python3 scripts/profile_experts.py --prompts work.txt \
    --out experts.json --print-offload
Measured on this rig's SQL/Python workload
hot/cold ratio5.6× — e47: 19,768 selections vs e49: 3,500
coldest 32 experts14.7% of activations (uniform would be 25%)
never selected0 — the tail is cold, not dead

Offloading the coldest 64 to host memory made the FP8 build faster, not slower — 97 → 180 tok/s at double the context — because the freed VRAM lets CUDA graphs capture fully. Accuracy was unchanged within noise.

Traps worth knowing

  • --cpu-offload-params alone does nothing. It only marks params eligible; nothing moves without a --cpu-offload-gb budget. Same VRAM, same KV cache, no error.
  • MTP does not work for this model. vLLM builds a 2816+1024 concat where the assistant checkpoint wants 2×2816. Fails identically on vLLM 0.25.1 and 0.26.0, NVFP4 and FP8 — a vLLM-side gap, not our setup.
  • Audio is impossible on the 26B: its config declares audio_config: null. Only the 12B has an audio encoder.

What the sweep shows

  • The 26B MoE is the sweet spot and it is not close. It beats the dense 12B by 8 points and runs twice as fast, because it activates only 8 of 128 experts per token while the 12B reads all of its weights every time. Model size and speed are not the same axis once a mixture-of-experts is on the table.
  • E2B is the speed king at 254 tok/s — 2.5× the 26B — and holds a 7.5M token KV cache. At 49.7% it is not a coding model, but for classification, routing, extraction or anything with a tight loop it is the obvious choice.
  • E4B doubles E2B's cost for +13 points. A reasonable middle for structured work that needs some judgement.
  • 4-bit costs more on smaller models. The 12B loses 5.5 points to quantization where the 31B loses 1.5. Less redundancy to spare.
  • Only the FP8 26B and the 31B reach a published mark. Everything at 4-bit sits below its card number, consistently — which is the same conclusion the quantization tests reached from the other direction.
Bug found while running this: the speed harness measured time-to-first-token by waiting on delta.content, but a reasoning model streams its first tokens into delta.reasoning_content. TTFT stayed None and the report crashed. On a model that thinks before answering, the first reasoning token is the first token.

Driving it from Gemini CLI

The whole of Google's Gemini CLI — hooks, MCP servers, subagents, checkpointing, plan mode, sandboxing, extensions — now runs against local Gemma, with no changes to the CLI at all. That last part is the point. The CLI stays byte-identical to upstream, so npm update keeps working forever and every feature Google ships arrives for free. Nothing here is a fork to maintain.

It works because the CLI honours GOOGLE_GEMINI_BASE_URL. Point it at a small Rust process that speaks Gemini REST at the front and OpenAI at the back:

gemma --boot                                    # vLLM on :8891
gemma-gateway --listen 127.0.0.1:8899 --upstream http://127.0.0.1:8891/v1
GEMINI_API_KEY=local GEMINI_CLI_TRUST_WORKSPACE=true \
GOOGLE_GEMINI_BASE_URL=http://127.0.0.1:8899 gemini

With no --model, the gateway discovers the model from vLLM's /models endpoint and follows profile switches. Pin --model only when the gateway fronts a separately fixed server.

Two settings are needed once, in ~/.gemini/settings.json: security.auth.selectedType: "gemini-api-key", because the CLI has a GATEWAY auth type that getAuthTypeFromEnv() returns but validateAuthMethod() does not accept — the feature is half-wired upstream. And GEMINI_CLI_TRUST_WORKSPACE=true for headless runs, which the trust gate otherwise blocks.

Running the verified work wave through Gemini CLI

WAVE_AGENT=gemini GEMMA_GATEWAY=http://127.0.0.1:8899 \
python3 scripts/pi_work_wave.py --workspace /path/to/project \
  --no-baseline-gate --final-verify true

This keeps the same queue, verification gates, retry budget, commits and stream-JSON capture; only the session driver changes from Pi to Gemini CLI.

Running the CLI's own router on a local model

Gemini CLI scores every request for complexity before doing any work, to decide which model should handle it. Left alone against a local backend, that scoring call goes to the full-size model — a wasted 26B call on every single turn.

Google's answer is gemini gemma setup: install their LiteRT-LM binary and download a Gemma 3 1B to do the scoring. But reading LocalLiteRtLmClient in the CLI bundle shows its client is just the GenAI SDK pointed at a base URL — v1beta generateContent, JSON response format, temperature 0, 256 tokens. That is this gateway's wire format exactly, so no LiteRT install is needed and the classifier can run on a model that has actually been benchmarked here:

"experimental": { "gemmaModelRouter": {
    "enabled": true,
    "autoStartServer": false,
    "classifier": { "host": "http://127.0.0.1:8899",
                    "model": "gemma3-1b-gpu-custom" } } }

Three things there are load-bearing and each cost real time to find. autoStartServer defaults to true and will hunt for a LiteRT binary that is not installed. The model name is checked against a hard-coded literal — "Only gemma3-1b-gpu-custom has been tested" — so it must be spelled that way regardless of what is served; harmless, because --model pins the real model and the requested name is discarded. And the reply is JSON.parsed under a 10-second timeout, so whatever sits behind the gateway must be fast and must honour response_format.

Verified working: with it wired up the gateway logs two inbound requests per turn — one streaming (the turn itself) and one not (the classifier).

What the gateway had to translate, and what broke

The two formats disagree in more places than the documentation suggests. Every row below was a real failure, found by running the CLI rather than by reading:

SymptomCauseStatus
Error executing tool generic_tool: Tool "generic_tool" not found — every tool call failed OpenAI streams one tool call across several SSE deltas: the first carries id and name, later ones append fragments of arguments with no name. Gemini's functionCall is atomic. Translating each chunk on its own emitted one nameless call per fragment. vLLM was returning the call correctly the whole time. fixed — accumulate by index, emit at finish_reason
Model answers confidently about an attached image it never saw inlineData and fileData parts were not read at all. Silent — no error, just a wrong answer. fixed — data-URL content parts, mime type picks image/audio/video
Grammar error: Invalid type: OBJECT, five retries, every turn Gemini's schemas are OpenAPI, whose type names are upper-case; vLLM compiles the schema into a decoding grammar and rejects that spelling. This is what broke the model router. The trap: the CLI sends upper-case types under a key named responseJsonSchema, so trusting the field name leaves it broken. fixed — convert on content, not on the label
Loop detection and chat compression misbehaving responseMimeType and toolConfig were dropped, so JSON mode and tool_choice never reached the server. "Must not call a tool" silently became "may". fixed
Finished turns report zero tokens used A streamed response carries no usage unless asked, and the final chunk that carries the counts has no choices — so it was being discarded. fixed — stream_options.include_usage
Turn crashes after the answer already arrived data: [DONE] is an OpenAI convention. Google's SSE just ends. Forwarding it makes the GenAI SDK JSON.parse the word [DONE]. fixed — swallow the sentinel
All of it is unit-tested without a server or a GPU — the translation layer is pure JSON in, JSON out, and 31 tests cover the shapes above including the two that were found only by capturing live traffic off the wire.

Lessons learned — including everything that did not work

Most of what follows are things that looked like the model failing and were not. That is the single biggest lesson from this build: on a local rig, a capable model spends most of its apparent failures being strangled by the harness around it. Each row below was diagnosed by measurement, not by guessing.

1. Nine times the "bad model" was a broken measurement

What it looked likeWhat it actually wasEffect once fixed
Model scores 0% on every benchmark Gemma's chat template sets enable_thinking|default(false). Turning thinking on without --reasoning-parser gemma4 is worse than leaving it off: 900+ tokens are generated and content comes back None. 0% → real scores

3. Gates that cannot fail are worse than no gate

  • A gate green before any work exists cannot judge anything. Four units shipped with a --present pattern matching a word the file already contained. A correct model and an idle one look identical; the only remaining requirement is that something gets committed. The driver now runs every gate at startup and warns.
  • She once "fixed" a file by deleting it. 45 lines of query logic replaced with // ... existing query processing .... The defect pattern was gone, the fix signature present, the file compiled, a commit existed — every check passed. Found by reading the diff, not by any automated check. There is now an elision guard, and her prompt says outright that a placeholder comment deletes code.
  • The gate is still weaker than it looks. A unit verified by a test suite can be passed by deleting the failing assert. Same class of hole, one layer out.
Found while writing this page, which is the point of writing it: 12B's GPQA run consumed two hours and produced no score. The sweep piped the benchmark straight into grep for the summary line, so a run that timed out and a run that scored zero both landed in the TSV as -, with every diagnostic discarded — and the page then rendered that as -%, which reads as a formatting glitch rather than a failure. The sweep now keeps each benchmark's full output in its own log, distinguishes TIMEOUT from ERROR by the exit status, and prints the tail loudly; the page shows the failure in red. Same lesson as above, one level up: it is not enough for a gate to be able to fail, the failure has to be visible.

4. Small samples lie

MMLU-Pro measured 87.5% at n=8 and 79.7% at n=350 on the same model and protocol. The first number would have been reported as a comfortable pass. Two earlier "passes" (MMLU-Pro 84%, MMMLU 87%) turned out to be artefacts of sampling the easy front of a category-ordered split — both evaporated under representative sampling.

Corollary: use the standard harness. lm-evaluation-harness is what produced the published numbers, and our own harness under-measured relative to it. Reimplementing an eval is reimplementing its bugs.

5. Published numbers are for full-precision weights

The card's marks were not measured on a quantized checkpoint. RedHat publishes its own evals of the quantized 26B, and ours matched them almost exactly — while both sit below Google's card:

BenchmarkOur measurementRedHat (quantized)Google card (full precision)
AIME 202580.0%80.0%88.3%
GPQA Diamond73.0%74.75%82.3%

So chasing some card numbers on a 4-bit model is chasing something that was never achievable. Knowing that early would have saved hours.

7. The router profile — a real skew, but no dead weight

The prediction was a power-law with experts specialised away from this workload, sitting idle. Measured over this rig's own SQL/Python prompts across all 30 layers:

hot/cold ratio5.6× — e47: 19,768 selections vs e49: 3,500
coldest 32 of 12814.7% of activations (uniform would be 25%)
never selected0 experts — the tail is cold, not dead

So the skew is real and offloading pays, but nothing can be discarded outright. Also: the hook had to target layers.N.router.proj — Gemma-4 does not use the gate name other vLLM MoE models do, so the obvious filter found nothing at all.

8. Infrastructure that bit hard

  • An unbounded compile took the whole machine down. The FP4 JIT runs one ninja job per core — 32 here, each peaking around 4.9 GB. That is ~157 GB against 61 GB of RAM. WSL died mid-load and wiped /tmp, taking the logs with it. MAX_JOBS=3 now bounds it; the artefacts cache, so it is paid once.
  • Logs lived in /tmp. The above erased them exactly when they were needed. Everything durable now lives in ~/gemma-logs, one file per boot.
  • A remote hook leaked 549 processes. The ssh shim's timeout killed the local client; the remote process has no TTY, never sees SIGHUP, and survives. 33 GB of dead RSS, swap exhausted, load average 241 on the LAN box. The deadline now runs remote-side.
  • Linking, three times. The pip CUDA wheels ship only versioned sonames (libcudart.so.13), and ld resolves -lfoo strictly through libfoo.so, so each kernel module failed on a different library in turn. Bridge the whole directory once.
  • The display drifts. Windows holds 0.7–1.8 GiB of the card and it moves between boots. At a 10 GiB offload budget the FP8 weights tipped into Available KV cache memory: -1.53 GiB and refused to start. 0.93 is the practical gpu-memory-utilization ceiling here.

9. Making her able to do the job at all

  • She said she had no internet — she had tools she never saw. Pi lists a skill by description and leaves opening it to the model. She saw rig-tools, tried to curl Google, hit a CAPTCHA, and concluded the network was unavailable. The commands now sit in her system prompt where they cannot be missed.
  • A Windows path silently became a relative one. C:\Users\... is not absolute to Pi, so it was glued onto the working directory. The file was never found, which read exactly like "she cannot see images".
  • Background sessions produced nothing at all. Zero-byte log, no files. Detached runs inherit a stdin that never delivers EOF, so Pi waited forever. </dev/null on the headless exec.
  • She looped verbatim until she hit the token cap. The driver exported GEMMA4_FREQUENCY_PENALTY — and nothing read it. There was no anti-repetition measure anywhere. Now applied server-side, so every client gets it.
  • Give her more turns, not fewer. The units she completed on turn 7–10 were the hard ones. Cutting at 6 turns does not save time; it discards nearly-finished work and reruns it from scratch.

10. The one habit that found all of it

Every item above was found the same way: reproduce the failure, then measure the fix. Not "the model seems weak" but "8 of 100 answers were truncated, and 74 + 8 = 82 which is the published mark". Not "offloading should be slower" but 97 → 180 tok/s on the same prompts. The two times measurement was skipped — trusting a ledger that said 33/33, and reporting a pass from an n=8 sample — both produced claims that were simply false.

And when a number cannot be reached honestly, say so. GPQA at 73% against a published 82.3% is a real gap on a quantized model, not a harness bug — dressing that up would have wasted more time than admitting it.

11. The bugs live in the seams, not in either system

Six failures came from joining Gemini CLI to vLLM, and not one was in Gemini CLI or in vLLM. Both were behaving correctly; the loss was entirely in the translation between them. The most expensive was the streaming tool-call bug, where vLLM had been returning read_file with the right arguments all along and the gateway was shredding it into nameless fragments. The diagnosis that mattered was testing vLLM directly with a hand-built request — the moment that came back correct, the search space collapsed to one file.

A second, sharper version of the same lesson: my first fix for the schema bug did not work, because I trusted a field named responseJsonSchema to contain JSON Schema. It contains OpenAPI. Check what is in the field, not what the field is called.

12. TurboQuant compresses the cache, not the weights

Worth being precise about, because the name gets used loosely. The paper (TurboQuant, Google Research, ICLR 2026) has no weight-quantization experiment in it at all. It quantizes KV-cache vectors and retrieval embeddings. Pointing it at a 26B checkpoint does nothing to the checkpoint.

The mechanism is genuinely elegant, and it is what makes the rest of this section make sense: multiply each vector by a random orthogonal matrix, which forces every coordinate into a predictable bell curve, then apply a scalar quantizer tuned for exactly that distribution. Because the rotation is orthogonal it loses no information and inverts exactly from a stored seed — the compression is entirely in the rounding. And because the rotation makes the distribution knowable rather than assuming it, no calibration data is needed.

That matters because real LLM tensors are not bell-curved — they have outliers orders of magnitude above the typical value, and one outlier forces the scale so wide that every ordinary value collapses into a couple of code points. The rotation spreads that outlier energy across all coordinates. It is not a compression step; it is what makes the compression step computable.

13. Going below 4-bit is a dead end for this model, for two separate reasons

The obvious idea — if 4-bit works, try 3-bit — fails twice over, and it is worth writing down because the reasoning is not intuitive.

vLLM will not do it. The compressed-tensors format packs 1–8 bits and the schemes exist, but both MoE code paths reject anything that is not 4 or 8 (assert self.num_bits == 4 or self.num_bits == 8). Since routed experts are roughly 89% of a 26B-A4B, a working 3-bit path would only shrink the parts that are not the problem.

And it would be slower. This is the part that inverts the intuition: the tensor-core instruction is selected by the activation dtype, not the weight dtype. Two-bit weights with 16-bit activations run at 16-bit speed. Fewer weight bits buy memory bandwidth and nothing else, which helps only at batch 1. On Blackwell, NVFP4 is the only format that reaches the FP4 tensor cores, and it measures 31% faster than 4-bit AWQ+Marlin at the same bit width with 56% lower time-to-first-token. Swapping it for something smaller would be slower at any real concurrency.

Also confirmed by reading the startup log rather than assuming: this rig is on FlashInferCutlassNvFp4LinearKernel with an sm_120 autotune cache hit — the native FP4 path, not the Marlin fallback. That fallback is a one-line warning, and taking it silently means paying NVFP4's accuracy cost at Marlin's speed. The check is now written into serve_vllm.sh next to the flag that depends on it.

14. The failure that returns a wrong answer instead of an error

Expert CPU-offload combined with a 4-bit MoE checkpoint, on this exact stack — sm_120 under WSL — loads without complaint, runs without error, and returns "" or "." where the answer belongs, on every MoE backend (vLLM #38718, still open). The companion report of the same combination crashing outright was closed not_planned after 90 days with no maintainer reply. vLLM additionally drops to pin_memory=False under WSL, so the path is degraded here by design.

This rig was never exposed, by luck rather than judgement: the quality profile offloads experts on an FP8 checkpoint, where offload is fine — and where it measured faster, 97 → 180 tok/s at twice the context, because the freed VRAM allowed full CUDA-graph capture. The launcher now refuses the combination that corrupts and says why.

Silent wrong answers are the worst failure this rig can have. Every other lesson in this document was found because something visibly broke. This one would have been found by nobody, and would have quietly poisoned a 33-unit bug wave. When a configuration is known to fail silently, the fix is not a note in a document — it is a refusal in the code.
